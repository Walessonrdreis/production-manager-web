# Implementação: Blindagens Shadow Read e Dual DB (Infraestrutura)

**Versão:** v4.24.2
**Data:** 2026-05-21
**Classificação:** Refatoração local / Proteção de Sistema

## O que mudou
- **Throttle/Cooldown no Shadow Read:** Modificado o `StockShadowReadService` para implementar um lock em memória (`COOLDOWN_MS = 60000`). Isso impede que requisições simultâneas ao endpoint disparem a comparação concorrentemente, evitando DoS interno e consumo alto de CPU/log.
- **Limitação de Logs (Amostragem):** A amostragem de dados legados no log foi mantida num escopo pequeno de "Top N diferenças" (`topDifferences.length < 5`) e agregada apenas como totais, isolando o console de payloads volumosos.
- **Diretriz Adicional Documentada (`AGENTS_MIGRATION.md`):** Adicionada regra rigorosa sobre como utilizar os dois `PrismaClients`: legacy para dados nativos legados e primary (oficial) para as tabelas externalizadas, prevenindo "Table does not exist".

## Por que mudou
- O Shadow Read, quando rodado a cada requisição, afeta a performance assíncrona (mesmo via setTimeout) podendo gerar picos de sobrecarga.
- Estabelecer a regra de fronteira do `Prisma` blinda o projeto contra desenvolvedores/agentes consumindo erroneamente models do Legado no Novo DB.

## Como validar
- O `Shadow Read` rodará na primeira consulta de Estoque. Se consultado sequencialmente de forma rápida, as próximas requisições processarão sem que o `console.log` de shadow read acione — atestando que a debouncing/throttle está operando.

## Como desfazer (Rollback)
- Reverter o serviço `StockShadowReadService.ts` omitindo a cláusula `this.lastRunTimestamp`.
